# Coze 智能体配置

## 1. 配置目标

在 Coze 中建立两个独立智能体：

| 智能体 | 建议名称 | 职责 |
| --- | --- | --- |
| A | ResumeMatch-JD-Score | 契合度百分比、评分维度、条目匹配、缺失要求 |
| B | ResumeMatch-Item-Suggestion | 已有条目的文本优化建议 |

两个智能体并行调用，不互相依赖。后端通过独立 Bot/Workflow ID 调用，并分别校验结果。

## 2. 后端环境变量

```dotenv
COZE_API_BASE_URL=https://api.coze.cn
COZE_API_TOKEN=
COZE_SCORE_AGENT_ID=
COZE_SUGGESTION_AGENT_ID=
COZE_TIMEOUT_SECONDS=30
```

真实 Token 和智能体 ID 不得提交到 Git。前端不得读取这些变量。

## 3. 公共输入变量

两个智能体都接收同一个 JSON 对象：

| 变量 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `analysisId` | string | 是 | 本次分析 ID，仅用于回显关联 |
| `resumeVersionId` | string | 是 | 简历版本 ID |
| `jdText` | string | 是 | 用户输入的完整 JD |
| `resumeDocument` | object | 是 | 脱敏后的结构化简历 |

完整示例见 [扣子公共输入.json](示例/扣子公共输入.json)。

### 3.1 脱敏规则

发送给 Coze 前，后端必须移除：

- `basicInfo.name`
- `basicInfo.phone`
- `basicInfo.email`
- `basicInfo.nativePlace`
- `basicInfo.birthDate`
- `basicInfo.gender`

允许保留 `jobTarget` 和公开作品链接。section ID、item ID、模块类型、字段和内容必须保留，以便模型返回可校验引用。

## 4. 智能体 A：契合度分析

### 4.1 系统提示词

```text
你是 ResumeMatch 的 JD 契合度分析智能体。你只负责评估，不负责改写简历。

输入包含 analysisId、resumeVersionId、jdText 和脱敏后的 resumeDocument。

任务：
1. 依据 JD 和简历中可验证的文字证据计算 0-100 的契合度。
2. 按固定四维评分：coreRequirements 满分 40、experienceEvidence 满分 30、skillsCoverage 满分 20、presentationQuality 满分 10。
3. 四个维度 score 之和必须等于 overallScore。
4. 为简历中与 JD 有关的条目返回 itemMatches。
5. 列出 JD 明确要求但简历没有证据的 missingRequirements。

强制规则：
- 只使用输入中出现的事实，不推断候选人具备未写明的能力。
- sectionId 和 itemId 必须原样引用输入中的 ID。
- 不得使用姓名、性别、年龄、出生年月、籍贯等个人属性评分。
- overallScore 必须是整数。
- scoreLevel：80-100 为 high，60-79 为 medium，0-59 为 low。
- itemMatches.level 只能是 high、medium、low。
- missingRequirements 只做缺失提示，不能写成候选人已经具备。
- 不输出建议文本，不输出简历改写。
- 只返回一个合法 JSON 对象，不使用 Markdown 代码块，不添加任何前后说明。
```

### 4.2 输出结构

完整示例见 [契合度智能体输出.json](示例/契合度智能体输出.json)。顶层只允许：

- `overallScore`
- `scoreLevel`
- `summary`
- `scoreBreakdown`
- `itemMatches`
- `missingRequirements`

### 4.3 后端校验

1. 总分和维度分均为整数且范围合法。
2. 维度名称、权重固定且不得重复。
3. 维度得分之和等于总分。
4. `scoreLevel` 与总分区间一致。
5. 所有 section/item 引用存在且归属正确。
6. `missingRequirements` 不得为空字符串或重复。

## 5. 智能体 B：条目优化建议

### 5.1 系统提示词

```text
你是 ResumeMatch 的简历条目优化建议智能体。你只负责优化已有条目的文字表达，不负责评分，也不生成整份简历。

输入包含 analysisId、resumeVersionId、jdText 和脱敏后的 resumeDocument。

任务：
1. 找出与 JD 相关但表达不够具体、清晰或聚焦的现有条目。
2. 对每个条目返回 original、suggested 和 reason。
3. suggested 应突出输入中已经存在的职责、技术和结果，并保持中文简历表达自然、简洁。

强制规则：
- sectionId 和 itemId 必须原样引用输入中的 ID。
- targetField 首版只能是 content。
- original 必须与输入 item.content 完全一致。
- 不得新增输入中没有的技能、工具、公司、学校、项目、职责、成果、数字或时间。
- 不得修改姓名、联系方式、学校、公司、岗位、项目名和日期等事实字段。
- 缺失但无法证实的 JD 要求不能写入 suggested。
- 没有安全改写空间的条目不要返回建议。
- suggested 不得等于 original。
- reason 说明改动目的，不得声称候选人拥有未提供的经历。
- 只返回一个合法 JSON 对象，不使用 Markdown 代码块，不添加任何前后说明。
```

### 5.2 输出结构

完整示例见 [条目建议智能体输出.json](示例/条目建议智能体输出.json)。顶层只允许 `suggestions`。

每条建议只允许：

- `sectionId`
- `itemId`
- `targetField`
- `original`
- `suggested`
- `reason`

### 5.3 后端校验

1. 所有 section/item 引用存在且归属正确。
2. `original` 与版本快照中的 `item.content` 完全一致。
3. `targetField` 为 `content`。
4. `suggested` 非空且不等于 `original`。
5. 同一条目最多保留一条建议。
6. 发现新增数字、专有名词或技术关键词时，与原条目和同一 item 的 fields 进行事实核对；无法找到依据则拒绝该建议。

## 6. Coze 输出设置

优先在 Coze 工作流中使用结构化输出或 JSON Schema 节点。若只能使用普通文本输出，应增加末尾校验节点，确保最终结果：

- 是单个 JSON 对象。
- 不包含 ```json 代码围栏。
- 不包含“以下是结果”等前缀。
- 不包含 schema 未定义字段。
- 数组为空时返回 `[]`，不返回 `null`。

## 7. 调用与超时

- 两个智能体由后端并行调用。
- 单个智能体默认超时 30 秒。
- 后端不在同一次请求内无限重试。
- 首次调用失败时记录 Provider 状态，由 `/retry` 接口显式重试。
- Coze 原始错误必须转换为项目错误码，不能直接返回给前端。

## 8. 上线前测试集

至少准备以下脱敏样本：

1. 高契合 JD：核心技能和经历均有明确证据。
2. 低契合 JD：大量要求未在简历中出现。
3. 同义词场景：JD 与简历使用不同术语表达同一技术。
4. 缺失硬要求：验证只提示缺失、不写入建议。
5. 数字幻觉场景：验证建议不会新增百分比、性能或用户量。
6. ID 注入场景：输入正文中包含类似 ID 的文字，验证模型只引用结构字段中的 ID。
7. 空建议场景：所有条目已清晰时允许返回空数组。

验收时不固定模型具体措辞，但必须验证 JSON 契约、评分范围、权重求和、引用有效性和禁止虚构规则。
