# 接口文档编写指南

本指南规定 ResumeMatch REST API 文档的统一写法。新增或修改接口时，实现、Pydantic 模型、JSON 示例和文档必须同步更新。

## 1. 编写目标

文档应让未参与开发的人能够独立理解业务目的、构造合法请求、解析响应、处理错误并编写契约测试。Swagger 用于调试，仓库文档用于解释业务语义、状态变化和边界条件。

## 2. 文件组织

```text
docs/<中文专题名>/
├─ 文档目录.md
├─ 接入概述.md
├─ 接口参考.md
├─ 数据结构.md
├─ 接口文档编写指南.md
└─ 示例/
  ├─ 示例目录.md
   └─ *.json
```

目录和文档文件可以使用中文名称；URL、JSON 字段、枚举和代码标识继续使用英文。完整 JSON 必须单独保存，Markdown 片段不能代替示例文件。

## 3. 单接口标准结构

每个接口依次包含：

1. 接口名称与业务用途。
2. 方法、路径和 Content-Type。
3. 请求参数表：参数、位置、类型、必填性、约束。
4. 完整请求或 cURL 示例。
5. HTTP 成功状态和完整响应。
6. 业务规则、副作用、覆盖和幂等性。
7. 全部预期错误码和客户端处理方式。

成功响应统一使用：

```json
{
  "data": {},
  "requestId": "req_example"
}
```

错误响应统一使用：

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "资源不存在。",
    "details": {}
  },
  "requestId": "req_example"
}
```

客户端只依赖 `error.code` 做逻辑判断。

## 4. 字段规范

- JSON 字段使用 `camelCase`。
- 资源 ID 使用 `<resource>Id`。
- 时间点使用 `At` 结尾，年月使用 `Date` 结尾。
- 可空字段明确标为 `type | null`。
- 无值对象字段返回 `null`，数组返回 `[]`。
- 日期时间使用带时区的 ISO 8601，年月使用 `YYYY-MM`。
- 枚举必须列出全部合法值，不得使用“等”。

## 5. 状态码

| 场景 | 状态码 |
| --- | --- |
| 查询成功 | 200 |
| 创建成功 | 201 |
| 请求格式错误 | 400 |
| 资源不存在 | 404 |
| 状态冲突 | 409 |
| 文件过大 | 413 |
| 媒体类型不支持 | 415 |
| 结构或业务校验错误 | 422 |
| 服务内部异常 | 500 |
| 外部依赖异常 | 502/503/504 |

## 6. JSON 示例规范

每个专题至少提供完整成功响应、关键业务请求和响应、部分成功或低置信度场景，以及关键错误响应。

所有示例必须：

- 可被标准 JSON 解析器解析。
- 与 `数据结构.md` 一致。
- 同一资源 ID 在不同文件中保持一致。
- 统计、问题和正文自洽。
- 不包含真实个人信息、密钥或本地路径。

## 7. 版本兼容

- PATCH：文案或示例修正，不改变契约。
- MINOR：新增兼容字段、接口或枚举。
- MAJOR：删除字段、修改类型、语义或状态流。

破坏性变更不得静默覆盖旧契约。

## 8. 安全要求

- 不记录或示例化真实 Token、密钥和个人信息。
- 错误详情不返回堆栈、SQL、本地路径或第三方原始响应。
- 文件上传接口明确大小、类型、签名校验和临时文件处理。
- 涉及个人信息时说明日志脱敏要求。

## 9. 提交前检查

- [ ] 方法、路径、Content-Type、状态码完整。
- [ ] 参数位置、类型、必填性和约束完整。
- [ ] 响应与 Pydantic 模型一致。
- [ ] 枚举和空值规则完整。
- [ ] 副作用、幂等性和状态变化已说明。
- [ ] 错误码稳定且覆盖关键分支。
- [ ] JSON 全部可解析。
- [ ] Markdown 本地链接有效。
- [ ] 不包含真实个人信息或密钥。
- [ ] 契约测试覆盖文档示例。
